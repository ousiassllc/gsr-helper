# 画面・キーバインド仕様

機能との対応は [機能要件](../requirements/functional.md)、Model の構成は [コンポーネント設計](../components/overview.md) を参照。本書で定める表示を構成する部品の階層と配置は [TUI コンポーネント設計](atomic-design.md) を参照。

## 設計原則

1. **有効なキーを常に画面に出す。** フッターに現在の画面で使えるキーを表示する。
2. **無効な操作は隠さずグレーアウトし、理由を示す。** 「なぜ押せないのか」が分かる状態を保つ（例: `run.sh 直起動のため systemd 操作は不可`）。
3. **小文字は安全側、大文字は影響が大きい側。** `x`（停止）に対して `X`（強制停止）、`d`（ドレイン停止）に対して `D`（削除）。
4. **色に依存しない。** 状態は記号でも判別できるようにし、`NO_COLOR` を尊重する。配色は端末の背景の明暗に合わせて切り替える。
5. **破壊的操作は影響を表示して `y/N`（既定 N）。** Enter の連打では進まない。
6. **操作の起点は複数、確認は 1 つ。** 一覧の直接キー・詳細画面の操作リスト・Jobs タブのいずれから起動しても、同じ確認ダイアログを経る（[FR-45〜FR-47](../requirements/functional.md)）。

## 共通レイアウト

```
┌────────────────────────────────────────────────────────────────────────────┐
│ gsr-helper   host: build01   root   gh: 認証済み                           │ ← ヘッダ
│ [1]Runners [2]Jobs [3]Disk [4]Logs [5]Doctor [6]Config [7]Setup            │ ← タブ
├────────────────────────────────────────────────────────────────────────────┤
│                                                                            │
│                            （本体）                                        │
│                                                                            │
├────────────────────────────────────────────────────────────────────────────┤
│ ⚠ 孤児ユニット 1 件 / 警告 2 件                          選択: 2 件        │ ← 状態行
│ s:開始 x:停止 X:強制 d:ドレイン D:削除 n:追加 u:更新 e:設定 l:ログ ?:ヘルプ │ ← フッタ 1 行目
│ (s)(x)(X)(R)(D)(n)(u): root 権限が必要です（sudo で起動してください）       │ ← フッタ 2 行目
└────────────────────────────────────────────────────────────────────────────┘
```

**本体以外が使う行数は 7 行に固定する**（ヘッダ 1 + タブ 1 + 区切り 1 + 区切り 1 + 状態行 1 + フッタ 2）。フッタが 1 行のときと 2 行のときで本体の高さが動くと、一覧の行数がフレームごとに変わって表示が跳ねるためである。無効な操作が無い場合もフッタ 2 行目は空行として確保する。

フッタ 2 行目には無効なキーの理由をまとめて出す。**同じ理由のキーを 1 つの組にまとめ、`(s)(x): 理由` の形で理由の数だけ空白 2 つ区切りで並べる。** キー自体は消さず、丸括弧で囲んで無効であることを色以外でも示す（設計原則 4）。

並べる順は、**最も多くのキーを塞いでいる理由を先頭**にし、残りは出現順とする。行に収まらない分は末尾を中略する。中略で削られるのは末尾からなので、最も広く当てはまる理由（root / systemd / 認証のような能力不足は複数のキーに一斉に効く）が最後まで残る。**件数（「他 N 件」）にまとめて捨てない**——まとめた理由はフッタから一切辿れなくなる。

フッタ 1 行目は `?:ヘルプ` を必ず含む。幅に収まらない場合は手前のヒントから落ち、`?:ヘルプ` だけが残る。全キーの一覧へ辿れる入口を画面ごとの作り方に委ねないためである。上のモックのフッタ 1 行目は 75 セルを使う。

ヘッダには能力判定の結果を出す。`root` が無い場合は `read-only`、`systemctl` が無い場合は `systemd なし`、`gh` が未認証なら `gh: 未認証` と表示し、依存する操作が使えないことを示す。

**`gh` の認証ユーザー名は出さない。** 認証済みでユーザー名が分からない状態は `gh: 認証済み` と表示する。能力判定（`Caps`）はトークンそのものを持たない設計であり、ユーザー名の取得には GitHub API を要するためである（API を使う機能が入った時点でユーザー名を出せるようになる）。

ディスク使用率もヘッダには出さない。集計は Disk タブの担当であり、未実装の値を置くと「集計中」と「取得失敗」を区別できない表示になる。

起動時のジョブ実行の前提チェック（[FR-44](../requirements/functional.md)）で不備が見つかった場合は、状態行に `⚠ ホスト前提 2 件（5 で詳細）` を加えて Doctor タブへ誘導する。判定は非同期なので、確定した時点で状態行に現れる。**ラベル欠落のようにジョブがエラーにならず queued で止まる種類の不備もあるため、警告は runner の稼働状態が正常でも出る。**

### 状態行

左側は検出結果から、右側は現在のタブから作る。同じ検出結果からの件数をタブごとに作らせないための分担である。

| 位置 | 内容 |
|------|------|
| 左 | `⚠ 孤児ユニット N 件` / `警告 N 件` / `✗ <検出エラー>` を ` / ` で連結する。いずれも該当が無ければ出さない |
| 右 | 現在のタブが報告する文（`選択: N 件` / `入力中: 絞り込み`） |

`✗ <検出エラー>` は検出そのものが期限内に終わらなかった場合に出す。**エラーで画面遷移を巻き戻さず、状態行に出すだけにする。** 一覧は直前に成功した内容を保つ。

無効なタブの番号キーを押した場合は、右側にその理由を出す（下記「タブの有効・無効」）。この打鍵ではタブが変わらないため、右側の報告より優先して表示する。

### タブの有効・無効

**タブ行には常に 7 枚すべてを出す。** 押しても何も起きないキーを作らないためである。実装のないタブはグレーアウトし、番号キーを押したら理由を状態行に出す。

```
 [3]Disk この版では未対応です
```

現時点で有効なのは `[1]Runners` と `[2]Jobs` の 2 枚で、`[3]`〜`[7]` は `この版では未対応です` を理由に無効である。`tab` / `shift+tab` は無効なタブを飛ばす。無効なタブへはキーも共有状態も配らない。

能力（`Caps`）でタブを無効にする枠も同じ仕組みを使う。実装済みの 2 枚はホスト内の読み取りだけで成立するため常に有効である（`systemctl` が無くても `run.sh` 直起動の runner を表示できる）。

### 一覧の自動更新

一覧は**タイマーで自動更新する**。`r` の手動再読み込みは、次の周期を待たずに同じ検出を発行するものである。

| 項目 | 値 |
|------|-----|
| 更新間隔 | 既定 3 秒。`--refresh` と設定の `refresh_interval` で変更でき、**下限は 1 秒** |
| 1 回の検出に許す時間 | 15 秒（更新間隔とは別の値） |

**更新間隔と検出の期限を切り離す。** 同値にすると `--refresh 1` のような短い間隔ではほぼ毎周期で期限切れになり、取れた分だけの部分結果が返る。部分結果ではユニットが紐付かない runner が出るため、systemd 管理の runner が `run.sh` / `-` と誤表示され、孤児ユニットも過少報告される。

| 規則 | 内容 |
|------|------|
| 二重起動しない | 実行中の検出があるうちは新しい検出を始めない（次の周期は必ず予約するので自動更新は止まらない）。`r` も同様に重ねない |
| 古い結果を採らない | 検出には周期の通し番号を付け、**直近に適用したものより古い結果は捨てる**。遅い周期が後から返って一覧が巻き戻ることを防ぐ |
| 期限切れの結果を採らない | 部分結果では上書きせず、直前の成功結果を保つ。期限切れは状態行の `✗ <検出エラー>` として出す |

二重起動を禁じるのは、1 回の検出が `systemctl show` を 8 並列で撒くためである。`systemctl` が応答しない——まさに検出が長引くその状況で——無条件に発行すると最大 5 周期が重なり 40 プロセスが同時に走る。

自動更新は API を呼ばない（[外部インターフェース](../api/external-interfaces.md#レート制限とエラー)）。

## Runners タブ

既定画面。ホスト上の runner 一覧。

```
  NAME          SCOPE        MANAGED   SVC        JOB       VERSION   _WORK
▸ build01-1     org:foo      systemd   ● active   ▶ 4m12s   2.311.0    31.2G
  build01-2     org:foo      systemd   ● active   idle      2.311.0     8.1G
  build01-3 ⚠   foo/bar      run.sh    -          idle      2.309.0     2.0G
  build01-4     org:foo      systemd   ○ inactive idle      2.311.0     0.4G
  build01-5 ⚠   org:foo      ?         ? unknown  idle      2.311.0     0.4G
  ─ 孤児ユニット ────────────────────────────────────────────────────────────
  actions.runner.foo-bar.old01.service   ✗ failed   （対応ディレクトリなし）
```

| 記号 | 意味 |
|------|------|
| `▸` | カーソル位置。行頭の固定の 1 セル |
| `[x]` / `[ ]` | 複数選択の状態（選択モード時のみ表示）。カーソルの**次**のセル |
| `● active` | サービス稼働中 |
| `○ inactive` | サービス停止中 |
| `✗ failed` | サービス異常終了 |
| `-`（SVC 列） | systemd ユニットなし |
| `? unknown`（SVC 列） | ユニットはあるが `systemctl show` に失敗して状態が取れなかった |
| `systemd` / `run.sh` / `-` / `?`（MANAGED 列） | 起動方式。[FR-03 の 4 状態](../requirements/functional.md#起動方式の-4-状態fr-03)。`?` は判定不能（ユニット一覧が取れなかった） |
| `▶ 4m12s` | ジョブ実行中と経過時間 |
| `idle` | ジョブなし |
| `⚠` | 行に注意事項あり（下記）。詳細は `enter` |

**SVC 列の `-` と `? unknown` は別の状態である。** 前者はユニットが存在しない（`run.sh` 直起動など）、後者はユニットは存在するが状態を取得できなかったことを表す。同じ記号にすると「サービス登録されていない」と誤読される。`?` は MANAGED 列の判定不能と同じ記号を使い、読み替えを要さないようにする。

**`⚠` は NAME 列の中（名前の直後）に描く。** 行末に置くと、`bubbles/table` が列幅を超えた分を切り落とすため記号が消える。名前の幅を記号の分だけ狭めることで、記号の有無にかかわらず列幅が変わらない。名前と記号を並べる余地が無い幅では名前を諦めて記号だけを描く（行に注意があることを示すのはこの記号だけなので、落とすと警告そのものが画面から消える）。

`⚠` の意味は「**この行は要注意である**」の 1 つだけで、次のいずれかに当てはまるときに付ける。

- サービスが異常終了している（`failed`）
- サービス制御ができないか、可否を判定できない（`run.sh` 直起動 = `MANAGED: run.sh`、または起動方式が判定不能 = `MANAGED: ?`）
- バージョンが読めない

判定不能（`?`）にも付けるのは、`run.sh` 直起動と分かっている runner より要注意だからである。ユニット一覧が取れておらず、サービス制御の可否すら決められない。バージョンの新旧の判定には最新版の取得（GitHub API）が必要で、権限異常の判定は Doctor タブの担当なので、この記号には含めない。

孤児ユニット（FR-05）は一覧の下部に別区画で表示する。**この区画に出すのは「対応する runner ディレクトリが見つからないユニット」だけ**で、次の 2 種は含めない（[FR-05 の除外](../requirements/functional.md#孤児ユニットに含めないものfr-05)）。いずれも警告として状態行の件数に含める。

- `systemctl show` に失敗して状態が取れなかったユニット（状態不明を「ディレクトリが消えた異常」として提示しないため）
- `LoadState=not-found` のユニット（`svc.sh uninstall` 後に参照だけが残った状態。runner ディレクトリは存在する）

### 詳細画面（`enter`）

行の `⚠` の内容確認と、キーを覚えていない場合の操作の起点を兼ねる（[FR-46](../requirements/functional.md)）。

```
 build01-1  詳細

  スコープ      org:foo
  起動方式      systemd（actions.runner.foo.build01-1.service）
  サービス      ● active / enabled
  ジョブ        ▶ 実行中 4m12s（foo/bar、Worker PID 284193）
  バージョン    2.309.0  ⚠ 最新は 2.311.0（disableUpdate=true）
  ディレクトリ  /opt/runners/build01-1
  work          /opt/runners/build01-1/_work（31.2G）

  操作
▸ l  ログを開く
  s  開始                              （稼働中のため不要）
  d  ドレイン停止（ジョブ完了を待つ）
  R  再起動
  E  enable / disable の切り替え
  e  設定を編集
  u  バージョン更新
  ────────────────────────────────────────────────────────
  x  停止
  X  強制停止（⚠ 実行中のジョブは中断されます）
  D  削除（⚠ 登録解除 + サービス削除）

 enter:実行  j/k:選択  esc:戻る
```

- **初期カーソルは常に安全側の先頭項目に置く。** 詳細を開き直すたびにリセットし、前回選んだ操作を覚えない。一覧の `enter` → 詳細の `enter` で破壊的操作に到達しないようにするための規則である。
- 破壊的な操作は区切り線の下に置き、警告色で影響を併記する。
- 実行できない操作は一覧と同様にグレーアウトし、理由を右側に示す（消さない）。**無効な項目は選択できるが実行できない**（`enter` を押しても何も起きない）。
- `enter` で選んだ操作が破壊的な場合は、一覧から直接キーを打った場合と同じ確認ダイアログへ進む。
- 詳細画面でも各操作キー（`s` / `x` / `X` / `d` / `R` / `E` / `e` / `u` / `D` / `l`）を直接打てる。直接キーも `enter` と同じ可否の判定を通るため、無効な操作では何も起きない。
- **開いている間も一覧と同じ周期で内容が更新される。** 対象の runner はディレクトリで引き直し、状態・可否・配色を作り直す。ただし**カーソルは動かさない**（操作を選んでいる最中に別の項目へ飛ばないため）。1 周期だけ対象が検出漏れした場合は直前の内容を保つ。対象そのものが変わったときはカーソルを先頭へ戻す（[FR-46](../requirements/functional.md)）。

#### 起動方式の行の表記

一覧の MANAGED 列は列幅の都合で 1 セルの記号に詰めるが、詳細画面では**何が分かっていないのかを文で示す**。

| 起動方式 | 詳細画面の表記 |
|---------|--------------|
| `systemd` | `systemd（<ユニット名>）`。ユニット名が無ければ `systemd` |
| `run.sh` | `run.sh（<ユニット名>）`。ユニット名が無ければ `run.sh` |
| 未稼働（`-`） | `未稼働（サービス登録なし・プロセスなし）` |
| 判定不能（`?`） | `判定不能（ユニット一覧を取得できませんでした）` |

サービスの行も同様に、ユニットが無い場合（`-`）とユニットはあるが状態が取れなかった場合（`? unknown`）を書き分ける。

### 端末幅による列の省略

幅が足りない場合、次の順に列を落とす。

1. `_WORK`
2. `VERSION`
3. `MANAGED`
4. `SCOPE`

`NAME` / `SVC` / `JOB` は常に表示する。**この順を使い切ってもなお収まらない場合は、残った列の末尾から落とす**（右側の列ほど補足的な情報である）。落とせる列が 1 つも無い区画（Jobs の `WORKER PID`、孤児ユニットの `NOTE`）でも桁が溢れないようにするためである。

**列が 0 個になることはない。** 最後の 1 列は幅が足りなくても残す（列が無いと見出しも行も描けず、空の表になる）。したがって極端に狭い幅では行が幅を超え得る。幅 60 未満では本体を描かず、表示不能である旨と必要な幅・現在の幅を出す。

この落とす順は runner を並べる一覧（Runners / 孤児ユニット / Jobs）のものである。別の列を持つタブ（Disk / Logs / Doctor）は自分の順を宣言する（[TUI コンポーネント設計](atomic-design.md#moleculecolumns-の契約)）。

## Jobs タブ

このホストで実行中のジョブを runner 横断で一覧する（[FR-04](../requirements/functional.md) の表示形態）。

```
  RUNNER        REPOSITORY          ELAPSED   WORKER PID   _work
▸ build01-1     foo/bar             4m12s     284193       /opt/runners/build01-1/_work/bar
  build01-7     foo/baz             22m03s    291044       /opt/runners/build01-7/_work/baz
```

実行中ジョブが無い場合はその旨を表示する。`l` で該当ジョブの Worker ログへ直接移動する。

**操作対象はジョブではなく runner である**（[FR-47](../requirements/functional.md)）。取り違えを防ぐため、フッタの先頭で対象を明示する。全キーに `runner を` を付けると幅 80 に収まらないため、対象の明示は先頭の `enter:runner の詳細` に代表させる。

```
 enter:runner の詳細  d:ドレイン  X:強制  R:再起動  l:ログ  ?:ヘルプ
```

操作の集合と表記は Runners タブのフッタと同じ定義から引く（`keymap.RunnerKeys.JobsFooter`）。**page 側で文言を書き直さない。** キーを差し替えたときに Jobs タブのフッタだけが古い表記のまま残るためである。削除（`D`）と設定編集（`e`）を出さないのは詳細画面から辿る操作としているためで、先頭の `enter:runner の詳細` がその入口になる。再起動（`R`）は逆に、Runners タブでは幅の都合でフッタに入れられなかったものをここで出す（Jobs タブは出すキーが少なく幅に余裕がある）。

- `enter` で当該 runner の詳細画面（上記）を開く。削除や設定編集はここから行う。
- ジョブ単体を中止する機能は持たない。ホスト側からは `Runner.Worker` を強制終了するしかなく、ジョブが失敗として記録されるため、中止は GitHub 側の操作に委ねる。

## キーマップ

### グローバル

| キー | 動作 |
|------|------|
| `1`〜`7` | タブの直接選択 |
| `tab` / `shift+tab` | 次 / 前のタブ |
| `r` | 手動で再読み込み |
| `?` | ヘルプ（全キーの一覧） |
| `q` / `ctrl+c` | 終了 |
| `esc` | 選択のクリア / 1 つ前の状態へ戻る |

グローバルキーが効かない状態が 2 つある。**入力中**（絞り込み・フィルタ・フォーム）と**モーダル表示中**である。いずれも後述する。`ctrl+c` はどちらでも有効。

`r` は次の周期を待たずに再読み込みを発行する（一覧は常にタイマーで更新されている。上記「一覧の自動更新」）。実行中の検出があるときは重ねない。

配送の実装上の規則（キーは現在のタブへ先に渡り、タブが使わなかったものだけがグローバルキーとして解釈される）は [TUI コンポーネント設計](atomic-design.md#キー入力の配送) に定める。**この規則は「入力中とモーダル表示中にグローバルキーが効かない」ことを画面側で保証するためのものである。**

|------|------|

| `enter` | 確定 |

**絞り込みの内容は本体の 1 行目に出す。**

```
 絞り込み: build01-1
```

この行は入力中と確定後の両方で出る（絞り込み文字列が設定されている間ずっと）。状態行の `入力中: 絞り込み` は入力中しか出ないため、確定後に何で絞っているかを画面に残すにはこの行が必要である。**この行は本体の高さを 1 行消費する**（一覧に配る行数がその分だけ減る）。

## 無効な操作の表示

操作できない場合はキーを消さず、グレーアウトして理由を示す。フッタ・詳細画面の操作リストのいずれでも同じ理由を表示する。

判定は次の順に行い、**最初に一致した理由を返す**。実装状況（未対応）の判定は最後に置く。能力の問題（root / systemd / 認証）を「未対応です」で隠すと、`sudo` で起動し直せば使えるのかどうかが読み取れなくなる。

| 順 | 状況 | 表示 |
|----|------|------|
| 1 | 非 root | `s/x/X/R/D/n/u: root 権限が必要です（sudo で起動してください）` |
| 2 | systemd が無い | `s/x/X/R/E/d: サービス制御は利用できません（systemctl が見つかりません）` |
| 3 | `run.sh` 直起動の runner | `s/x/R: systemd 管理外のため操作できません` |
| 4 | 起動方式が判定不能 | `s/x/R/E: systemd の管理状態が判定できないため操作できません（ユニット一覧を取得できませんでした）` |
| 5 | `gh` 未認証 | `n/D/u: GitHub の認証が必要です（gh auth login）` |
| 6 | スコープ不足（**判定は未実装**） | `n/D: org レベルの操作には admin:org が必要です（gh auth refresh -h github.com -s admin:org）` |
| 7 | ジョブ実行中 | `D: ジョブ実行中です。先に d でドレイン停止してください` |
| 8 | **この版で未実装の操作** | `この版では未対応です` |

`run.sh` 直起動より先に systemd の不在を見るのは、`systemctl` が無ければ起動方式にかかわらずサービス制御ができないためである。

「起動方式が判定不能」が塞ぐのは `s`（開始）/ `x`（停止）/ `R`（再起動）/ `E`（enable / disable の切替）の 4 つだけである。実行経路が「systemd 管理かどうか」に依存する操作に限る。`X`（強制停止）と `d`（ドレイン停止）は worker のプロセスに作用するので使え、`l`（ログ）/ `e`（設定）/ `u`（更新）も管理経路に依存しない。

「スコープ不足」は**判定を実装していない**。保有スコープの確認には GitHub API が必要で、その機能を持ち込む Issue が判定を足す。それまで `n` / `D` は認証の有無（5）までで判定する。

`この版では未対応です` は無効なタブの理由（上記「タブの有効・無効」）と同じ文言を使う。利用者にとって両者は「この版ではまだ使えない」という同じ意味であり、同じ意味の文言を 2 箇所に持つと片方だけが直る。

グレーアウトと理由を出すのは **フッタと詳細画面の操作リスト**である。`?` の全キー一覧は可否を反映せず、その画面で使えるキーをすべて載せる（可否は状況で変わるため、一覧の役割はキーと動作の対応を示すことに限る）。
