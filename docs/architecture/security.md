# セキュリティ設計

本ツールは **root 権限（`sudo` での起動）を前提**とし、runner の登録権限を持つ GitHub トークンを扱う。したがって設計上の最大の関心は「誤操作と情報漏洩を構造的に防ぐこと」である。

前提は [アーキテクチャ設計](overview.md)、扱うファイルは [データモデル](data-model.md) を参照。

## 守る対象と脅威

| 守る対象 | 脅威 | 主な緩和策 |
|---------|------|-----------|
| ホスト上のファイル | root 権限での誤削除（パス誤り、シンボリックリンク経由の逸脱） | 削除パスの検証、ドライラン、二段確認 |
| 実行中のジョブ | 意図しない中断 | ジョブ実行中の操作ガード、ドレイン停止を既定に |
| GitHub トークン | 画面・ログ・監査ログへの漏洩、プロセス引数からの読み取り | メモリ保持のみ、マスク、下記の制約の明示 |
| runner の登録状態 | 誤った登録解除、意図しないアカウントでの登録 | 対象の明示と確認、トークン取得元の固定 |
| 操作の追跡可能性 | 何をしたか分からなくなる | 全外部コマンドの監査ログ記録 |

## root 権限で動作することへの対応

`sudo` での起動を選択したため、**すべての破壊的操作が root 権限で実行される**。バグや入力誤りの被害が大きくなるため、以下を構造として強制する。

### 1. 削除パスの検証を必須にする

削除を行う関数は、対象パスの検証を通過しない限り実行できない構造にする。検証手順:

1. 対象パスを絶対パス化する
2. 対象パスとその基準ディレクトリ（runner ディレクトリ）の**両方**をシンボリックリンク解決した上で比較する
3. 対象が基準ディレクトリの**配下**にあることを確認する（基準ディレクトリ自身は削除対象にしない）
4. さらに削除が許可されたサブツリー（`_work` / `_diag`）配下であることを確認する
5. パス要素に `..` が含まれる場合は拒否する

**シンボリックリンクの扱い**: 検証時は経路の逸脱を防ぐためリンクを解決するが、**削除時はリンクを辿らない**。ツリーを削除する際は各エントリを `Lstat` で判定し、シンボリックリンクはリンク自体のみを削除する。これを取り違えると、`_work` 内のリンクが指す外部のファイルを消しかねない。

異常系（`..` を含むパス、基準外への絶対パス、基準からリンクで外に出るパス、基準ディレクトリ自身）は必ずテストで網羅する。

### 2. 確認を経ない破壊的経路を作らない

削除・停止・登録解除は共通して「対象と影響の提示 → 実行コマンド全文の表示 → 承認 → 実行 → 結果報告 → 監査ログ」の順を踏む。承認を省略する引数やショートカットは実装しない。

### 3. ジョブ実行中の操作をガードする

`Runner.Worker` が存在する runner に対しては、`_work` 配下の削除、登録解除、強制停止をブロックし、ドレイン停止を提案する。

### 4. 設定と状態ファイルの所有者に注意する

root で動作するため、無防備に作成したファイルは root 所有になる。**設定ファイルは実行ユーザー（`SUDO_USER`）の設定ディレクトリに、その所有権で作成する。** そうしないと、次に非 root で起動したときに自分の設定が読めなくなる。

| ファイル | 所有者 | パーミッション |
|---------|-------|--------------|
| 設定ファイル（YAML） | `SUDO_USER` | 600 |
| 監査ログ | root | 600（ディレクトリは 700。下記の但し書き） |
| バックアップファイル | 元ファイルと同一 | 元ファイルと同一 |

**既存のディレクトリのパーミッションは変更しない。** 700 の保証は**本ツールが作成したディレクトリに限る**。`/var/log` や他の所有者のディレクトリを再パーミッションしないためである。したがって `audit_log` の親が既にもっと緩いモードで存在する場合、そのモードのまま使う（ファイル自体は常に 600 で作る）。運用側で緩いディレクトリを使う場合は、そのモードの妥当性を運用手順で担保すること。

設定ファイルのディレクトリについても同様で、`--config` で対象ユーザーのホームの外を指した場合は chmod も chown も行わない。ホームの外にある `gsr-helper` という名前のディレクトリを 0700 かつ非特権ユーザー所有に変えると、本ツールへの `sudo` だけを許されたユーザーにとって権限昇格になるためである（[コンポーネント設計](../components/overview.md#設定ファイルの配置とパーミッションappconfigconfpath)）。

出力先を開く際はシンボリックリンクを辿らない（`O_NOFOLLOW`）。開いた後は同じ fd 上で通常ファイル・ハードリンク数 1・所有者が実効 UID であることを確かめる。差し替えられた出力先へ書かないためである。

## トークンの扱い

### 取得の優先順

1. 環境変数 `GH_TOKEN`
2. `sudo -u $SUDO_USER gh auth token`（`SUDO_USER` があり、かつ実効 UID が 0 のとき）
3. `gh auth token`

`sudo` で起動すると `gh auth token` は **root の gh 設定**を参照するため、通常のユーザーで済ませた認証が読めない。2 番目の経路がこれを回避する。

### 保持と出力

- **ファイルに保存しない。** 取得したトークンはプロセスのメモリ上のみで保持する。
- **画面に表示しない。** 認証状態は「認証済み / 未認証」とアカウント名のみを示す。
- **ログに出力しない。** デバッグログにも含めない。
- registration token / remove token も同様に扱う。短命（既定 1 時間）だが、有効な間は runner の登録・解除ができる強い権限を持つ。

### 監査ログでのマスク

監査ログには実行コマンドの全文を記録するため、**マスクを二重にかける**。

1. **キー名によるマスク** — 秘密情報を伴うオプション名の直後の値を `***` に置換する
2. **値の一致によるマスク** — メモリ上で保持しているトークン文字列と一致する引数を `***` に置換する

1 だけではオプション名が想定外だった場合に漏れる。2 だけでは記録時点で解放済みのトークンに対応できない。両方を `exec` 層に実装し、呼び出し側がマスクを忘れられない構造にする。

#### 1. キー名によるマスクの対象

| 判定 | 対象の名前 |
|------|-----------|
| 完全一致 | `token` / `pat` / `jitconfig` / `password` / `secret` |
| 部分一致 | `authorization` / `bearer` / `apikey` / `api-key` / `api_key` |

名前は先頭のハイフンを除いて小文字で突き合わせる（`-token` / `--Token` / `--TOKEN` は同じキー）。**部分一致に `token` を含めない**のは、`--tokens`（複数形のリスト指定など）のように秘密情報でない名前まで巻き込むためである。連続して同じキーが並ぶ形（`--token --token SECRET`）でも実際の値が素通りしないこと。

値の位置は 2 通りある。

| 形 | 扱い |
|----|------|
| `KEY=VALUE` を 1 引数で渡す | キー名を残して `=` の右だけを置換する。**ハイフンが無くてもよい**（`TOKEN=xxx` のような環境変数形式も拾う。`=` の右は必ず値なので誤爆しない） |
| `--key VALUE` と 2 引数で渡す | **キー側にハイフンが必要。** 位置引数（`gh secret set NAME`）にまで反応すると、秘密でない次の引数を潰して実行コマンド全文の追跡可能性を削るためである |

キー名は必ず残す。何のオプションが渡されたかは監査ログとして残す必要があるためである。

`-H` / `--header` は**ヘッダ名が秘密情報らしい場合に限り、`Name:` の後ろの値だけ**を置換する。`-H Accept: application/vnd.github+json` はそのまま残り、`-H Authorization: Bearer X` は `Authorization: ***` になる。ヘッダ全体を置換すると、どのヘッダを送ったのかが監査ログから分からなくなる。

#### 2. 値の一致によるマスクの下限

**値の一致によるマスクは 8 文字未満の秘密情報を対象にしない。** 短い文字列はコマンド行のどこにでも偶然一致し、コマンド全体が `***` で埋まって監査ログが読めなくなるためである。GitHub のトークンはいずれもこの長さを大きく超える。**この下限はキー名によるマスク（1）には適用しない**——キー名で秘密と分かる値は長さを問わず必ず置換する。

#### 実行前のプレビュー

確認ダイアログに出す実行コマンド全文も同じマスクを通す（UI 側でマスクを実装しない。[TUI コンポーネント設計](../ui/atomic-design.md#molecule-一覧)）。`Executor` は `Run` 1 メソッドに固定されているためプレビュー用のメソッドを持たない。呼び出し側が `exec/mask` の関数を**マスクすべき秘密情報を明示して**呼ぶ。

### 子プロセスへの環境変数の継承（既知の制約）

**外部コマンドは親プロセスの環境変数をすべて継承する。** 実行ごとに指定できる環境変数は「追加」であって置き換えではない。したがって `GH_TOKEN` を環境変数に置いて起動した場合、本ツールが起動する**すべての**子プロセス（`systemctl` / `docker` / `gh` / `config.sh` / `svc.sh`）がその値を受け取る。

これは `config.sh` などが動作に必要な環境（`PATH`・プロキシ設定・ロケール）を欠かさないための選択である。緩和は次のとおり。

- **`GH_TOKEN` を環境変数に置く必要はない。** 既定の取得経路は `gh` の認証情報の借用であり（上記「取得の優先順」）、環境変数はそれが使えない場合の手段である。
- 継承した値が引数として現れない限り、`/proc/<pid>/cmdline` からは読み取れない。ただし `/proc/<pid>/environ` は同一ユーザーと root から読める。
- 環境変数はマスクの対象外である（監査ログには記録しない）。**記録しないことは他プロセスから読めないことを意味しない。**

### プロセス引数からのトークン読み取り（既知の制約）

runner の登録は `config.sh --token <TOKEN>` の形でしか行えず、**トークンがプロセスの引数としてカーネルに渡る**。Linux では既定で他ユーザーからも `/proc/<pid>/cmdline` が読めるため、登録処理が走っている間、同一ホストの他プロセスからトークンを読み取れる。

これは runner 本体の仕様に由来する制約であり、本ツールでは回避できない。以下で緩和する。

- **追加・削除の操作前に、ジョブ実行中の runner がある場合は警告する。** self-hosted runner のジョブは任意のコードを実行するため、ジョブ稼働中にトークンを引数として渡すことが最も危険な状況になる。
- **doctor で `/proc` の `hidepid` 設定を確認する。** `hidepid=2` でマウントされていれば他ユーザーからの読み取りを防げる。設定されていない場合は情報として提示する。
- **トークンの有効期限に依存しすぎない。** 取得したトークンは使用後すぐに参照を破棄する。

## 外部コマンド実行の安全性

- **シェルを経由しない。** 外部コマンドは実行ファイルと引数配列を直接渡して起動する。シェル経由で組み立てる経路を作らないため、メタ文字によるコマンド注入は成立しない。
- **オプションインジェクションを防ぐ。** ユーザー入力をコマンド引数に渡す際、`-` で始まる値を拒否する。runner 名やラベルに `--config` のような値が入ると、後続の引数がオプションとして解釈される。
- **入力を検証してから渡す。**

| 入力 | 検証内容 |
|------|---------|
| runner 名 | 文字種（英数・`-`・`_`・`.`）、長さ、先頭が `-` でない、ホスト内での重複なし |
| ラベル | 文字種、長さ、重複なし、予約ラベル（`self-hosted` / `linux` / `x64`）でない、先頭が `-` でない |
| インストール先 / work dir | 絶対パス、`..` を含まない、書き込み可能、残容量が十分 |
| job hooks のスクリプトパス | 絶対パス、存在する、実行可能。**このパスは runner がジョブごとにシェルで実行するため、設定できる値であることの意味を UI に明示する** |
| URL / スコープ | ホストが GitHub であること |

- **すべての実行にタイムアウトを設ける。** 応答しないコマンドで UI が固まらないようにし、`context` でキャンセルできるようにする。

## ネットワーク

- GitHub API と tarball の取得は HTTPS のみ。
- **runner の tarball は SHA-256 を検証してから展開する。** 検証に失敗した場合は展開せず中止する。
- プロキシ環境変数を尊重し、doctor で設定の整合性を確認する。

## 監査ログ

本ツールが実行したすべての外部コマンドを JSON Lines で記録する（スキーマは [データモデル](data-model.md)）。**例外は下記「記録対象外とする読み取り専用の定期実行」の 1 種のみである。**

- 記録は `Executor` の実装内で行う。ドメイン層が `os/exec` を直接呼ぶことを禁止しているため、記録漏れが構造的に発生しない。
- 記録内容: 日時、実効 UID、`SUDO_USER`、操作の識別子、対象 runner とディレクトリ、コマンドと引数（マスク済み）、終了コード、所要時間、エラー。
- 追記は 1 レコードずつ行い、書き込みが途中で切れても以降のレコードが読めるようにする。
- **`error` フィールドにコマンドの出力を入れない。** 終了コードが 0 でない場合は「マスク済みのコマンド行が終了コード N で失敗した」ことだけを記録する（[データモデル](data-model.md#error-フィールドに入れるもの)）。出力には権限情報や資格情報が混ざり得るため、`sudo -l -U <user>` に限らず全てのコマンドでこの規則を適用する。標準エラー出力は画面向けのエラー文言にだけ含める。

### 記録対象外とする読み取り専用の定期実行

**Runners タブの再検出が発行する `systemctl list-units` / `systemctl show` は記録しない。**

理由は、記録すると監査ログが読み取りで埋まり、**本来記録すべき破壊的操作のレコードが押し流される**ためである。再検出は 3 秒ごとに `list-units` 1 本とユニット数ぶんの `show` を発行する。runner 20 台なら 1 分あたり約 8,400 行になり、`logrotate` に委ねているローテーションが数分で回って `svc.stop` / `runner.add` の記録が消える。「全外部コマンドを記録する」を貫くと、追跡可能性という当初の目的そのものが失われる。

記録しないことによる追跡可能性の損失は無い。対象は**ホストの状態を読むだけで何も変更しないコマンド**に限り、かつ利用者の操作を伴わない自動的な実行だからである。何を読んだかではなく何を変えたかが監査の対象である。

| 規則 | 内容 |
|------|------|
| 指定の方法 | `exec.Options.SkipAudit` を真にする（[コンポーネント設計](../components/overview.md#実行ごとのオプションoptions)） |
| 既定 | **偽（記録する）。** 記録漏れが既定にならないよう、記録しないことは呼び出し側の明示的な意思表示でしか起きない |
| 対象 | 再検出の `systemctl list-units` / `systemctl show`（`internal/runner/systemd` の `Scan`）。成功・失敗とも記録しない（失敗も 3 秒ごとに積み上がるため） |
| 対象外 | 破壊的操作（`svc.*` / `runner.*` / `disk.clean`）は従来どおり全件記録する。利用者の操作で発行する読み取りコマンド（doctor の `sudo -l -U` など）も記録する |

**「読み取り専用だから記録しない」ではない。** 記録しないのは、利用者の操作と無関係に高頻度で自動発行され、記録が他のレコードを押し流す実行だけである。

### 記録できない場合

出力先を開けない、または検証に落ちた場合は**記録せずに起動を続け、標準エラー出力に警告を出す**（挙動の詳細は [コンポーネント設計](../components/overview.md#監査ログを開けない場合の縮退)）。ホスト内の状態を読むだけの一覧表示が、ログの出力先の権限で使えなくなることを避けるためである。

**この縮退の間、「全外部コマンドの監査ログ記録」という統制は効いていない。** 記録が要件である運用では、起動時の警告を失敗として扱う手順を用意すること（例: ラッパースクリプトで標準エラー出力を検査する）。ツール側で「記録できなければ起動しない」動作にはしていない。

実行中の記録の書き込み失敗も、実行そのものを失敗にはしない。失敗件数を集計し、画面を閉じた後にまとめて標準エラー出力へ出す（TUI の実行中に標準エラー出力へ書くと描画が壊れる）。

**終了時にログを閉じられなかった場合も同じく報告する。** 閉じる時点でバッファに残ったレコードが書けなかった可能性があり、捨てると「記録されたはずのレコードが無い」ことに誰も気付けない。開けなかった場合と記録に失敗した場合が警告として出るのに、閉じ損ないだけが利用者に見えない状態を作らない。

## 非 root で起動された場合

読み取り可能な範囲で動作し、権限が必要な機能を無効化して理由を表示する（[アーキテクチャ設計](overview.md#起動シーケンスと能力判定) の能力判定）。権限不足を検出せずに実行して失敗するのではなく、**操作を選べない状態にしてから理由を示す**。

## パスワード不要 sudo の要求への対応

ワークフロー側の都合で、runner 実行ユーザーにパスワード不要の `sudo` が要求されることがある（`setup-*` 系アクションが `sudo install` でバイナリを `/usr/local/bin` へ置くなど）。doctor はこの有無を検出する（[FR-43](../requirements/functional.md)）が、**本ツールは付与を行わない。**

| 論点 | 方針 |
|------|------|
| 危険性の明示 | `NOPASSWD: ALL` の付与は、その runner で実行される **任意のワークフローに実質 root を与える**ことを意味する。self-hosted runner を public リポジトリで使う場合は特に危険である |
| 判定の強さ | 欠落は **WARN** とし FAIL にしない。必要かどうかはワークフローの内容で決まるため、ツールが一律に「不備」と断定しない |
| 対処 | 対処コマンドは表示のみ。sudoers の編集は失敗すると `sudo` 自体が使えなくなるため、`visudo -c` による検証を含めた手順を提示するに留める |
| 絞り込みの提案 | `NOPASSWD: ALL` ではなく、必要なコマンドに限定した記述を併せて提示する |

`sudo -l -U <user>` の出力は権限情報であるため、監査ログには実行事実と終了コードのみを記録し、出力内容は記録しない。この規則は監査ログ全体に適用してある（上記「監査ログ」）。

判定対象のユーザーは `Runner.RunAsUser` で、**ユーザー名が解決できない場合は UID の 10 進表記になる**。`sudo -l -U` は UID を `#1001` の形式でしか受け付けないため、数値を渡す場合は `#` を付ける（[データモデル](data-model.md#runasuser-の決定と-uid-フォールバック)）。付けずに渡すと「ユーザーが存在しない」という失敗になり、`NOPASSWD` が無い場合と区別できない。

## 実装しないこと

- 本ツール自身での権限昇格（`sudo` の内部実行、setuid、polkit 連携）は行わない。権限は起動時に決まったものを使う。
- **sudoers の書き換え、パッケージのインストール、`usermod` によるグループ変更は行わない。** doctor は検出と手順の提示までを担う。sudoers の破壊は復旧手段を失わせるため、自動化しない。
- リモートホストへの接続機能は持たない（スコープ外）。
- トークンの永続化・キャッシュは行わない。
