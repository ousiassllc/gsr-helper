# セキュリティ設計

本ツールは **root 権限（`sudo` での起動）を前提**とし、runner の登録権限を持つ GitHub トークンを扱う。したがって設計上の最大の関心は「誤操作と情報漏洩を構造的に防ぐこと」である。

前提は [アーキテクチャ設計](overview.md)、扱うファイルは [データモデル](data-model.md) を参照。

## 守る対象と脅威

| 守る対象 | 脅威 | 主な緩和策 |
|---------|------|-----------|
| ホスト上のファイル | root 権限での誤削除（パス誤り、シンボリックリンク経由の逸脱） | 削除パスの検証、ドライラン、二段確認 |
| 実行中のジョブ | 意図しない中断 | ジョブ実行中の操作ガード、ドレイン停止を既定に |
| GitHub トークン | 画面・ログ・監査ログへの漏洩、プロセス引数からの読み取り | メモリ保持のみ、マスク、下記の制約の明示 |
| runner の登録状態 | 誤った登録解除、意図しないアカウントでの登録 | 対象の明示と確認、トークン取得元の固定 |
| 操作の追跡可能性 | 何をしたか分からなくなる | 全外部コマンドの監査ログ記録 |

## root 権限で動作することへの対応

`sudo` での起動を選択したため、**すべての破壊的操作が root 権限で実行される**。バグや入力誤りの被害が大きくなるため、以下を構造として強制する。

### 1. 削除パスの検証を必須にする

削除を行う関数は、対象パスの検証を通過しない限り実行できない構造にする。検証手順:

1. 対象パスを絶対パス化する
2. 対象パスとその基準ディレクトリ（runner ディレクトリ）の**両方**をシンボリックリンク解決した上で比較する
3. 対象が基準ディレクトリの**配下**にあることを確認する（基準ディレクトリ自身は削除対象にしない）
4. さらに削除が許可されたサブツリー（`_work` / `_diag`）配下であることを確認する
5. パス要素に `..` が含まれる場合は拒否する

**シンボリックリンクの扱い**: 検証時は経路の逸脱を防ぐためリンクを解決するが、**削除時はリンクを辿らない**。ツリーを削除する際は各エントリを `Lstat` で判定し、シンボリックリンクはリンク自体のみを削除する。これを取り違えると、`_work` 内のリンクが指す外部のファイルを消しかねない。

異常系（`..` を含むパス、基準外への絶対パス、基準からリンクで外に出るパス、基準ディレクトリ自身）は必ずテストで網羅する。

### 2. 確認を経ない破壊的経路を作らない

削除・停止・登録解除は共通して「対象と影響の提示 → 実行コマンド全文の表示 → 承認 → 実行 → 結果報告 → 監査ログ」の順を踏む。承認を省略する引数やショートカットは実装しない。

### 3. ジョブ実行中の操作をガードする

`Runner.Worker` が存在する runner に対しては、`_work` 配下の削除、登録解除、強制停止をブロックし、ドレイン停止を提案する。

### 4. 設定と状態ファイルの所有者に注意する

root で動作するため、無防備に作成したファイルは root 所有になる。**設定ファイルは実行ユーザー（`SUDO_USER`）の設定ディレクトリに、その所有権で作成する。** そうしないと、次に非 root で起動したときに自分の設定が読めなくなる。

| ファイル | 所有者 | パーミッション |
|---------|-------|--------------|
| 設定ファイル（YAML） | `SUDO_USER` | 600 |
| 監査ログ | root | 600（ディレクトリは 700） |
| バックアップファイル | 元ファイルと同一 | 元ファイルと同一 |

## トークンの扱い

### 取得の優先順

1. 環境変数 `GH_TOKEN`
2. `sudo -u $SUDO_USER gh auth token`（`SUDO_USER` があり、かつ実効 UID が 0 のとき）
3. `gh auth token`

`sudo` で起動すると `gh auth token` は **root の gh 設定**を参照するため、通常のユーザーで済ませた認証が読めない。2 番目の経路がこれを回避する。

### 保持と出力

- **ファイルに保存しない。** 取得したトークンはプロセスのメモリ上のみで保持する。
- **画面に表示しない。** 認証状態は「認証済み / 未認証」とアカウント名のみを示す。
- **ログに出力しない。** デバッグログにも含めない。
- registration token / remove token も同様に扱う。短命（既定 1 時間）だが、有効な間は runner の登録・解除ができる強い権限を持つ。

### 監査ログでのマスク

監査ログには実行コマンドの全文を記録するため、**マスクを二重にかける**。

1. **キー名によるマスク** — `--token`、`--pat`、`--jitconfig` などの直後の値を `***` に置換する
2. **値の一致によるマスク** — メモリ上で保持しているトークン文字列と一致する引数を `***` に置換する

1 だけではオプション名が想定外だった場合に漏れる。2 だけでは記録時点で解放済みのトークンに対応できない。両方を Executor 層に実装し、呼び出し側がマスクを忘れられない構造にする。

### プロセス引数からのトークン読み取り（既知の制約）

runner の登録は `config.sh --token <TOKEN>` の形でしか行えず、**トークンがプロセスの引数としてカーネルに渡る**。Linux では既定で他ユーザーからも `/proc/<pid>/cmdline` が読めるため、登録処理が走っている間、同一ホストの他プロセスからトークンを読み取れる。

これは runner 本体の仕様に由来する制約であり、本ツールでは回避できない。以下で緩和する。

- **追加・削除の操作前に、ジョブ実行中の runner がある場合は警告する。** self-hosted runner のジョブは任意のコードを実行するため、ジョブ稼働中にトークンを引数として渡すことが最も危険な状況になる。
- **doctor で `/proc` の `hidepid` 設定を確認する。** `hidepid=2` でマウントされていれば他ユーザーからの読み取りを防げる。設定されていない場合は情報として提示する。
- **トークンの有効期限に依存しすぎない。** 取得したトークンは使用後すぐに参照を破棄する。

## 外部コマンド実行の安全性

- **シェルを経由しない。** 外部コマンドは実行ファイルと引数配列を直接渡して起動する。シェル経由で組み立てる経路を作らないため、メタ文字によるコマンド注入は成立しない。
- **オプションインジェクションを防ぐ。** ユーザー入力をコマンド引数に渡す際、`-` で始まる値を拒否する。runner 名やラベルに `--config` のような値が入ると、後続の引数がオプションとして解釈される。
- **入力を検証してから渡す。**

| 入力 | 検証内容 |
|------|---------|
| runner 名 | 文字種（英数・`-`・`_`・`.`）、長さ、先頭が `-` でない、ホスト内での重複なし |
| ラベル | 文字種、長さ、重複なし、予約ラベル（`self-hosted` / `linux` / `x64`）でない、先頭が `-` でない |
| インストール先 / work dir | 絶対パス、`..` を含まない、書き込み可能、残容量が十分 |
| job hooks のスクリプトパス | 絶対パス、存在する、実行可能。**このパスは runner がジョブごとにシェルで実行するため、設定できる値であることの意味を UI に明示する** |
| URL / スコープ | ホストが GitHub であること |

- **すべての実行にタイムアウトを設ける。** 応答しないコマンドで UI が固まらないようにし、`context` でキャンセルできるようにする。

## ネットワーク

- GitHub API と tarball の取得は HTTPS のみ。
- **runner の tarball は SHA-256 を検証してから展開する。** 検証に失敗した場合は展開せず中止する。
- プロキシ環境変数を尊重し、doctor で設定の整合性を確認する。

## 監査ログ

本ツールが実行したすべての外部コマンドを JSON Lines で記録する（スキーマは [データモデル](data-model.md)）。

- 記録は `Executor` の実装内で行う。ドメイン層が `os/exec` を直接呼ぶことを禁止しているため、記録漏れが構造的に発生しない。
- 記録内容: 日時、実効 UID、`SUDO_USER`、操作の識別子、対象 runner とディレクトリ、コマンドと引数（マスク済み）、終了コード、所要時間、エラー。
- 追記は 1 レコードずつ行い、書き込みが途中で切れても以降のレコードが読めるようにする。

## 非 root で起動された場合

読み取り可能な範囲で動作し、権限が必要な機能を無効化して理由を表示する（[アーキテクチャ設計](overview.md#起動シーケンスと能力判定) の能力判定）。権限不足を検出せずに実行して失敗するのではなく、**操作を選べない状態にしてから理由を示す**。

## パスワード不要 sudo の要求への対応

ワークフロー側の都合で、runner 実行ユーザーにパスワード不要の `sudo` が要求されることがある（`setup-*` 系アクションが `sudo install` でバイナリを `/usr/local/bin` へ置くなど）。doctor はこの有無を検出する（[FR-43](../requirements/functional.md)）が、**本ツールは付与を行わない。**

| 論点 | 方針 |
|------|------|
| 危険性の明示 | `NOPASSWD: ALL` の付与は、その runner で実行される **任意のワークフローに実質 root を与える**ことを意味する。self-hosted runner を public リポジトリで使う場合は特に危険である |
| 判定の強さ | 欠落は **WARN** とし FAIL にしない。必要かどうかはワークフローの内容で決まるため、ツールが一律に「不備」と断定しない |
| 対処 | 対処コマンドは表示のみ。sudoers の編集は失敗すると `sudo` 自体が使えなくなるため、`visudo -c` による検証を含めた手順を提示するに留める |
| 絞り込みの提案 | `NOPASSWD: ALL` ではなく、必要なコマンドに限定した記述を併せて提示する |

`sudo -l -U <user>` の出力は権限情報であるため、監査ログには実行事実と終了コードのみを記録し、出力内容は記録しない。

## 実装しないこと

- 本ツール自身での権限昇格（`sudo` の内部実行、setuid、polkit 連携）は行わない。権限は起動時に決まったものを使う。
- **sudoers の書き換え、パッケージのインストール、`usermod` によるグループ変更は行わない。** doctor は検出と手順の提示までを担う。sudoers の破壊は復旧手段を失わせるため、自動化しない。
- リモートホストへの接続機能は持たない（スコープ外）。
- トークンの永続化・キャッシュは行わない。
