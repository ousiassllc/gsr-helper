# 非機能要件

対象は Linux + systemd 上の self-hosted runner ホスト。機能一覧は [機能要件](functional.md)、権限とトークンの扱いは [セキュリティ設計](../architecture/security.md) を参照。

## 応答性・性能

| 項目 | 目標 | 根拠・備考 |
|------|------|-----------|
| 起動から一覧表示まで | 1 秒以内 | ディスク走査・`/proc` 走査・`systemctl` 参照のみ。ディスク使用量の集計は含めない。起動時の能力判定はこの内側に収める（下記） |
| 一覧の自動更新間隔 | **既定 3 秒**（設定で変更可。有効範囲 1〜3600 秒） | ジョブの開始・終了が体感で即時に見える間隔。`/proc` と `systemctl` のみなので負荷は軽い |
| 1 回の検出に許す時間 | 15 秒 | 自動更新間隔とは別の値。同値にすると短い間隔で部分結果が返り、起動方式を誤表示する（[画面仕様](../ui/screens.md#一覧の自動更新)） |
| キー入力への反応 | 常に即時 | 重い処理を UI スレッドで走らせない（下記） |
| 想定 runner 台数 | 1 ホストあたり 20 台程度まで実用的 | これを超える場合は `systemctl show` の並列度が支配的になる |

### UI をブロックしない処理

以下は非同期に実行し、結果が判明した分から順に画面へ反映する。

| 処理 | 扱い |
|------|------|
| ディスク使用量の集計 | 対象ごとに非同期集計。判明順に反映し、集計中であることを表示する |
| 到達性チェック（doctor） | 各チェックを並列実行。タイムアウトは個別に設定する |
| tarball のダウンロードと展開 | 進捗を表示し、キャンセルできる |
| `config.sh` / `svc.sh` の実行 | 実行中の表示と出力の逐次反映。一括処理では何台目かを表示する |
| ドレイン停止の待機 | 待ち時間は無制限。経過時間を表示し、任意のタイミングでキャンセルできる |
| ログのライブテール | ファイル監視で追記を検知して反映する |
| 起動時のジョブ実行の前提チェック（[FR-44](functional.md)） | 一覧表示をブロックせず非同期に実行し、判明した時点でヘッダと状態行に警告を出す |

`systemctl show` は runner ごとの実行になるため、台数が増えた場合は並列に実行する（同時実行数 8）。

**起動時の能力判定（`Caps`）は同期的に行い、全体を 800 ms で打ち切る**（1 プローブあたり 500 ms）。root と `systemctl` / `journalctl` の有無はプロセスを起動せずに判定でき、外部プロセスを起動するのは docker とトークンの 2 つだけなので並行実行する。上の「1 秒以内」を満たす保証はこの 800 ms の上限のみである。構造的には「先に一覧を描画してから能力判定の結果を `Msg` で折り込む」方が望ましいが、現時点では採っていない。

## 信頼性

- **部分的な失敗で全体を止めない。** 1 つの runner の設定ファイルが壊れていても、他の runner の表示は継続する。読み取りに失敗した項目は警告として集約し、画面上で確認できるようにする。
- **依存コマンドの欠落に耐える。** `systemctl` / `docker` / `journalctl` が存在しない環境ではエラー終了せず、該当機能を無効化して理由を表示する（縮退動作）。
- **外部コマンドには必ずタイムアウトを設ける。** すべての外部プロセス実行を `context` でキャンセル可能にし、応答しないコマンドで UI が固まらないようにする。
- **破壊的操作の前に必ず確認を挟む。** 確認を経ない削除・停止・登録解除の経路を実装しない。
- **ジョブ実行中の保護。** ジョブ実行中の runner に対する破壊的操作（`_work` の削除、登録解除、強制停止）はガードし、警告とドレイン停止の提案を出す。
- **失敗の可視化。** 一括処理では成功した台と失敗した台、失敗理由を実行後に一覧で提示する（[FR-15](functional.md)）。

## 安全性

詳細は [セキュリティ設計](../architecture/security.md)。非機能要件としての要点のみ記す。

- 本ツールは **root 権限（sudo での起動）を前提**とする。したがって削除系の処理は対象パスの検証を必須とし、runner ディレクトリ配下であることを確認してから実行する。
- GitHub のトークンはファイルに保存せず、メモリ上のみで扱う。画面・ログ・監査ログのいずれにも出力しない。
- 本ツールが実行したすべての外部コマンドに加え、**外部コマンドを伴わない破壊的操作（`internal/disk` のファイルの再帰削除）も監査ログに記録する**。監査ログの契約は当初「`exec` の実行実装が起動した外部コマンドだけ」だったが、`os.Remove` を直接呼ぶファイル削除は `Executor` を通らず記録が残らなかったため、「外部コマンドと、それに準ずる破壊的操作」へ広げてある（[Issue #71](https://github.com/ousiassllc/gsr-helper/issues/71)）。**記録の起点は層ごとに 1 箇所に固定する**——外部コマンドの実行実装（`internal/exec/command`）は `Run`、`internal/disk` は `removeTarget`——ため、対象を広げても記録漏れは構造的に増えない（[セキュリティ設計](../architecture/security.md#監査ログ)）。**例外は 2 種で、再検出（`internal/runner/systemd` の `Scan`）が発行する読み取り専用の `systemctl list-units` / `systemctl show` と、ログ追従（`internal/logs` の `Journal`）が発行する `journalctl -u <unit> -n <N>` は記録対象外とする**（`exec.Options.SkipAudit`。既定は記録する。理由と規則は [セキュリティ設計](../architecture/security.md#記録対象外とする読み取りコマンド)）。再検出は自動更新と手動再読み込み（`r`）のどちらで起動されたかを問わない。破壊的操作（`svc.*` / `runner.*` / `disk.clean`）は、外部コマンドを伴うものも `internal/disk` のファイルの再帰削除も全件記録する。**ただし、外部コマンドを伴わない破壊的操作で記録の起点を持つのは現時点では `internal/disk` だけである。** Config タブによる `.env` / systemd drop-in / `config.yaml` の置換（`internal/config` 系・`internal/appconfig`）と `internal/setup/tarball` による展開先の置換は `internal/audit` を経由せず、記録が残らない。この 2 つの発行元を経由しない読み取りコマンドも全件記録する。

| `fsnotify/fsnotify` | ファイル監視 | ログのライブテールでポーリングを避ける。`inotify` を直に扱わずに済み、Linux 以外でも同じコードが動く | 導入済み（`internal/logs` の `Tail`）。**追加ではなく直接依存への昇格である**——`golangci-lint` の推移依存として `go.mod` に既に載っていた |
| `gopkg.in/yaml.v3` | 設定ファイルの読み書き | 自前設定を人が手編集できる形式（コメント可）にするため。監査ログは JSON Lines なので標準ライブラリで扱う | 導入済み |

**Charm の 4 つ（bubbletea / bubbles / lipgloss / huh）は v2 系で揃える。** bubbletea v1 と v2 ではキー入力の `Msg` の型が異なり、周辺ライブラリの版を混ぜると `tea.Model` の実装が噛み合わない。版を上げる場合は 4 つ同時に上げる。

**v2 系のモジュールパスは `charm.land/<name>/v2` である**（`github.com/charmbracelet/<name>` ではない）。`huh` も同じ体系（`charm.land/huh/v2`）で追加してある。`github.com/charmbracelet/*` が間接依存として `go.mod` に現れるのは v2 系が内部で使っているためであり、直接 import してはならない（幅計算とカラープロファイルの判定が二重になる）。`bubbles/progress` を使い始めたことで増えた `github.com/charmbracelet/harmonica`（バーのばね補間）もこれに当たる。

この禁止は `golangci-lint` の `depguard` で機械的に強制している（[環境構築 / golangci-lint](../environment/setup.md#golangci-lint)）。`github.com/charmbracelet` 以下を直接 import すると `make lint` が失敗する。

**表示幅を数えるライブラリを追加しない。** 幅の計算は `lipgloss.Width` に一本化する（`go-runewidth` を併用すると、絵文字や結合文字を含む行で `bubbles/table` の列幅と 1 桁ずれる）。

## 保守性・テスト

### 設計上の制約

テスト可能性を保つため、以下を構造として強制する。

- **パースと判定ロジックを I/O から分離する。** ファイル読み取り・コマンド実行を行う関数と、その出力を解釈する関数を分ける。後者は純粋関数としてテストする。
- **外部コマンド実行を interface で抽象化する。** `systemctl` / `svc.sh` / `config.sh` / `docker` の実行を interface 越しに行い、テストでは差し替える。
- **検出結果の突き合わせを純粋関数にする。** ファイル・systemd・プロセスの 3 経路のマージは、正規化済みの入力を受け取る純粋関数として実装する。

### テスト方針

パーサと判定ロジックの単体テストを中核とする。

| 対象 | 方法 |
|------|------|
| `.runner` のパース | testdata のフィクスチャ。UTF-8 BOM 付き、キー欠落、不正 JSON を含める |
| スコープ判定（repo / org / enterprise） | テーブルテスト |
| `systemctl list-units` / `systemctl show` の出力パース | 実機出力を testdata に固定。行頭記号付き、値が空のケースを含める |
| 3 経路のマージと起動方式の判定 | 純粋関数へのテーブルテスト。孤児ユニット、走査外 runner、ディレクトリ重複を網羅 |
| 連番の決定（命名規則） | テーブルテスト。既存 runner の名前一覧から次の連番を導く |
| 削除パスの検証 | 対象パスが runner ディレクトリ配下であることの判定。`..` やシンボリックリンクを含む異常系を必ず含める |
| 外部コマンドを伴う処理 | interface を差し替え、発行されるコマンド列を検証する |
| UI の表示部品 | `atom` / `molecule` / `template` を純粋関数として期待文字列と比較する。幅・全角・列の省略順を含める |
| UI の状態を持つ部品 | `organism` / `page` にキー入力列を与え、状態遷移と発行される `tea.Msg` / `tea.Cmd` を検証する |

- **バグ修正には回帰テストを必ず添える。** 修正前に失敗し、修正後に通るテストを最も近いテストスイートに追加する。
- **画面全体を描画したスナップショットテストは初版では行わない**（画面変更のたびに更新が必要で保守コストが見合わない）。部品単位の期待値テストはこれに含めず、上記のとおり実施する（[TUI コンポーネント設計](../ui/atomic-design.md#テストの配置)）。

### CI

GitHub Actions の GitHub ホストランナー（`runs-on: ubuntu-latest`）で以下を実行する。前提は [環境構築 / GitHub ホストランナーで動かす](../environment/setup.md#github-ホストランナーで動かす) を参照。

- `gofmt` による整形チェック（`make fmt-check`）
- `go vet`（`make vet`）
- `golangci-lint`（`make lint`）
- 行数チェック（`make linterly`）
- Git Hooks 定義の検証（`go tool lefthook validate`）
- テスト（`make test` = `go test -race ./...`。[テストは常に競合検出付きで実行する](../environment/setup.md#テストは常に競合検出付きで実行する)）
- ビルド検証（`make build`）

## ユーザビリティ

- **操作可能なキーを常に画面に表示する。** 現在の画面で有効なキーをフッターに出し、無効な操作はグレーアウトして理由を示す（例: `run.sh` 直起動 runner の systemd 操作）。
- **破壊的操作は視覚的に区別する。** 確認ダイアログで対象と影響範囲を明示し、警告色を使う。
- **最小端末サイズは 80x24。** これを下回る場合は列を省略し、さらに狭い場合は表示不能であることを伝える。
- **色に依存しない。** 状態は記号と文字でも判別できるようにし、`NO_COLOR` 環境変数を尊重する。配色は端末の背景の明暗に合わせて切り替え、明背景の端末でも読める状態を保つ。
- **入力中はキーの扱いを変える。** 絞り込み・フィルタ・フォームの入力中はグローバルキーを解釈せず、入力中であることを状態行に示す（[画面仕様](../ui/screens.md#入力中絞り込みフィルタフォーム)）。
- **表示言語は日本語。** 画面上のラベル・メッセージ・確認文言は日本語で統一する。外部コマンドの出力はそのまま表示する。

## 制約

- **root 権限が必要。** `systemctl` / `svc.sh` / 他ユーザーの `/proc/<pid>/exe` の読み取りに root が必要なため、`sudo` での起動を前提とする。非 root で起動した場合は読み取り可能な範囲で動作し、権限不足の機能を無効化して理由を表示する。
- **GitHub API への到達が必要な機能がある。** runner の追加・削除・ラベル操作・最新バージョン確認はネットワークと有効なトークンを必要とする。オフライン時はこれらを無効化し、ホスト内の情報のみで動作する。
- **`gh` CLI に依存する。** トークンは `gh` の認証情報を借用する。`gh` が未認証の場合は該当機能を無効化して案内を出す。
